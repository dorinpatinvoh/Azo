2. Popup de proposition du Zem (DEMANDE_BACKEND_POPUP_PROPOSITION_ZEM.md)

Problème : quand un Zem acceptait une demande, le client n'était pas alerté et n'avait pas le temps de regarder le profil du Zem.

  • Événement temps réel ride:offered envoyé au client avec le profil public du Zem (jamais de téléphone, d'identifiant ni de nom complet), le prix, le trajet et un compte à rebours calé sur l'heure du serveur.
  • Notification poussée dédiée (canal Android « ride-offers », durée de vie = délai de la proposition), envoyée sans bloquer la réponse au Zem.
  • GET /rides/offers/pending : rattrapage si le client rouvre l'application.
  • POST /rides/:id/offer-seen : le Zem apprend que le client regarde son profil.
  • Marge de confirmation de 5 s après la fin du compte à rebours (latence réseau) ; salle personnelle user:{id} rejointe dès la connexion.
  • Nouvelle colonne offerSeenAt (migration 20261012130000) ; 23 tests ajoutés.

3. Fin de proposition : le Zem n'est plus bloqué (DEMANDE_BACKEND_FIN_PROPOSITION_ZEM.md)

Problème : quand le client refusait ou ne répondait pas, le Zem restait figé sur « 0 s » : le serveur lui répondait 403 et ne lui envoyait aucun événement.

  • Nouvelle table RideOffer (migration 20261012140000) : historique de chaque proposition et de son issue (acceptée, refusée, expirée, retirée, annulée).
  • GET /rides/:id : un Zem dont la proposition vient de finir reçoit une vue restreinte avec offerOutcome (24 h) — jamais la position, le téléphone ni le nom complet du client ; un Zem sans proposition reste en 403.
  • GET /rides/offers/current : proposition en cours et dernière terminée (10 min), pour reprendre après un redémarrage.
  • Événements ride:offer-ended, ride:offer-approved et ride:status MATCHED envoyés directement au Zem.
  • Notifications poussées à l'expiration et au refus ; erreur RIDE_OFFER_ENDED en 409.

4. Tests corrigés (7 échecs historiques)

  • Odometer (3) : les tests attendaient l'ancien tarif du Zem électrique ; le tarif en vigueur (base 120 F, paliers 60/50/45, commit 5a3b3bd0) donne 180, 210 et 300 F. Tests alignés. Point d'attention : la note de tarification.json et la demande « prix au kilomètre » annoncent encore un autre tarif électrique (base 100 F, 70/60/50) : à trancher avec l'équipe.
  • Radar client (4) : le code demande et renvoie maintenant le pseudo sous forme displayName / firstName ; tests alignés.

5. Arrêt anticipé avec code d'arrivée

Besoin : si la course s'arrête après quelques mètres, le client doit confirmer avec un code, comme au départ, et l'argent ne part qu'à ce moment.

  • stop-accept ne règle plus : il enregistre l'acceptation (stopAcceptedAt, migration 20261012150000), génère le code d'arrivée visible du client et prévient les deux parties.
  • POST /rides/:id/complete avec le bon code règle la distance réellement parcourue (prix figé à la demande) : le client est débité, le Zem crédité moins la commission ; le Zem n'a pas à être à destination.
  • Après acceptation, l'arrêt ne peut plus être refusé ni annulé ; il expire après 2 minutes si le code n'est pas saisi (le code disparaît, la course continue).
  • Réponses : stopRequest expose accepted et codeRequired. 3 tests ajoutés/remplacés.

6. Limites et suites

  • Ces flux sont testés en tests automatiques et vérifiés en ligne (routes présentes, commit déployé), mais pas encore avec deux vrais téléphones.
  • Pas de route GET /pricing côté serveur (le mobile utilise le barème embarqué).
  • Render (offre gratuite) s'endort : premier appel lent (~50 s) ; la tâche d'expiration ne tourne pas pendant la veille (un rattrapage existe à la lecture).
  • Règle de sécurité respectée : le fichier .env n'a jamais été lu ni reproduit.
